## Findings

### W8-R1 (2) The Main Phase hook consumes a modifier id in every game: the `mod-<id>` of EB02-030's replacement moves
- **Code:** `flow.ts` `runTurn`, the `main` step: `fireDelayedMain(d, p, d.s.nextMod++);`. The batch number is taken before `fireDelayedMain` knows whether any entry fires (`if (now.length === 0) return;` is inside the function), so `nextMod` grows by one at every Main Phase of every game. `nextMod` is also the id of a created replacement: `addReplacement` names its ability `mod-${d.s.nextMod}` (`run.ts`), and that name is inside the modifier that `hash.ts` serialises (`const { id: _id, ...rest } = m` drops the modifier's `id` but keeps `ab`, whose `id` is `mod-<n>`). Batch numbers and removal groups are canonicalised by position in the hash, so this is the only place the counter reaches it.
- **Probe:** p1 (Leader ST04-001, rested V.c1, EB02-030 and a card in hand, 2 active DON!!) ends its turn; p2 attacks V.c1; p1 uses the Counter; the replacement modifier exists. Output at the head of this branch: `nextMod` 7, ability `mod-6`, and the `mods` entry of `summary()` begins `{"ab":{"id":"mod-6",...`. With the allocation moved after the early return (temporary, reverted: `fireDelayedMain(d, p, -1)` and `batch = d.s.nextMod++` after `if (now.length === 0) return;`): `nextMod` 6, ability `mod-5`. So the same recorded game (same seed, same actions) holds a different state hash in this build than in the one before the wave, whenever a game with EB02-030 has the replacement alive at a hash point. The write-up's "no recorded game plays out differently ... the golden games and the 2,000-game property run replay with the same hashes" is true for play, and for hashes of every game without EB02-030, which is the only script that uses `addReplacement` (docs/reviews/m6b-leftovers.md, LF-R1). The per-game scripts hash does not move for EB02-030 records (it is not one of the six), so replay would not warn.
- **Why it matters:** replay and the stored-record hash checks (ADR 0004) are the reason the version is bumped; here one id changes without a bump and without a warning. Narrow (one card, hash only, not play), hence 2.
- **Fix:** take the batch lazily: `fireDelayedMain(d, p)` and `const batch = d.s.nextMod++` after the `now.length === 0` return, exactly as in the probe. Add a planted test: the replacement's ability id after two turns equals what it was before the wave (`mod-5` in the position above), or the hash of that position. If the lead prefers to keep the code, bump `ENGINE_VERSION` and re-record, and change the DECISIONS sentence.

### W8-R3 (1) The delayed order prompt has no timing word for the new timing
`flow.ts` `TIMING_WORDS` has no entry for `startOfOpponentsNextMainPhase`, so if two of the opponent's delayed entries are ordered (two Luffys), the `order` options read "Monkey.D.Luffy : <label>" with a stray space and no timing, unlike `endOfThisTurn` ("(at the end of this turn)"). Fix: add `startOfOpponentsNextMainPhase: '(at the start of the opponent\'s next Main Phase)'` (a prompt text only; it changes no state).

### W8-R4 (1) D8 defers an entry created earlier in the same turn, before the Main Phase begins
`fireDelayedMain` takes entries with `x.turn < d.s.turn`. The engine mutant `<=` survives every test, because every entry a scripted card can make (PRB02-005, [Your Turn]) is created in its controller's own turn, when the target Main Phase is in a later turn. A future card whose effect creates such an entry during the opponent's Refresh, Draw or DON!! phase (for example an [Opponent's Turn] auto) would have its "next Main Phase" be the one that is about to start, which `<` skips to the turn after. No card does this; record it next to `Delayed.at` so a later script is checked against it (the sound condition is "created before this Main Phase began", for example a phase stamp on the entry, not `turn <`).

### W8-R5 (1) Single-suite kills
Five mutants die in one suite only (Method 8a): OP12-041 `baseCost` 3 to 4, the pick `upTo` to `exactly`, OP15-014 `baseCost` to `cost` and OP16-079's duration are killed by the independent suite alone; OP12-041's DON!! add `upTo` by the author suite alone. The author tests do not pin the boundary of 3 (a cost-4 Event next to a cost-3 one), the "choose none" case, the Rush duration or "base cost" for Bartolomeo. Add them to the author files.

### W8-R6 (1) Data: ST14-014 has a truncated type
`cards/data` gives ST14-014 "Gum-Gum Giant Rifl" the type `Straw Hat Cre` (and the name is cut). The card is `verified: false` and a [Counter]-only Event, so it is not a Sanji candidate today; but every exact `{ type: 'Straw Hat Crew' }` filter will miss it, and a later fix that gives it a [Main] would need the type repaired first. Not part of the batch; record it with the verification backlog.

### W8-R7 (1) The OP15-119 rows are neither cited nor tested
The `faq_op15-eb04.txt` rows for OP15-119 settle two readings of this wave in the same direction as the build (Sabo's hand activation does trigger "when your opponent activates an Event", Reiju's trash activation does not), and the write-up cites neither. Plant them (probe in Method 3 is five lines on `OP15-119`) and add them to M6b-Q28 as confirming rows.
