## Performance

**Method (one place, all numbers).** A static server (`scripts/serve-dist.ts`) serves `app/dist` with gzip and `cache-control` like GitHub Pages; Lighthouse runs against it (`scripts/lighthouse.ts`, the `lighthouse` npm package with `chrome-launcher`, Playwright's Chromium), at the **desktop form factor** with a fixed throttle: 4× CPU slowdown, 40 ms RTT, 10 Mbit/s; the median of 3 runs (5 at release), cold cache, on `/`, `/cards`, `/play?scenario=late&opp=pirate&speed=step`, `/meta`, `/learn`, `/rules`. Every number is written to `test-results/lighthouse.json` with the Lighthouse version, the throttle and each run's score; the nightly asserts a **bound** (performance median ≥ 85, accessibility median ≥ 90 per route) and prints the requirement (90) beside the observed value, per `docs/runbooks/testing.md` §2. The release gate (WP10) is the requirement itself: median ≥ 90 on the release candidate, reported. Nothing about Lighthouse or frames runs per push.
Desktop, not Lighthouse's default mobile profile: below the board's minimum size the app shows "The board needs a bigger screen" by design (accessibility PD-5), so a mobile run would measure that screen. A mobile-profile run is recorded once for information.

- **First paint (WP1, BACKLOG §12).** `main.tsx` awaits `initStore()` (IndexedDB open and migrate, capped at 3 s) before the first render. The page shell, Home, Cards, Meta, Rules and the Learn pages paint at once; the store opens in parallel. Routes that need it (Play, Decks, Reviews, Progress, Settings → Data, the coach's profile) render a `StoreGate`: a skeleton and "Opening your saved data…" in a `role="status"`, replaced when ready (or after the 3 s cap, in memory mode, as today). The synchronous readers (`tutorial/timing.ts`, `progress/store.ts`, `coach/profile.ts`) read through the gate, so no reader sees an unready store. `index.html` carries a no-script line and an inline boot style so the first frame is not white. Target: first playable board under 3 s on the throttled profile (Lighthouse's LCP on `/play`, and an e2e that starts a game with IndexedDB delayed by 2 s and asserts the shell is visible first, on a fake clock for the delay).
- **Bundle (WP2).** Initial JS 83.5 KB gz stays under a **100 KB** cap (tightened from 300 so it cannot creep). New: a per-route table in `scripts/bundle-budget.ts` (the entry plus each lazy route's static imports, gz, by route), printed on every build and capped for the Game route once the baseline is known (set at baseline × 1.1, recorded in DECISIONS). The shared ai chunk (196 KB raw) carries the lethal solver the Game route needs only when the coach is opened; if the baseline shows the Game route over its target, the solver becomes a dynamic import behind the coach's first open (a loading state; the same engine answer). The two worker chunks (482 and 476 KB raw) are off the main thread and are not on this budget; they are reported.
- **Lighthouse performance (WP2).** Fix what the baseline names, in this order of likelihood: font preload and `font-display` for the two variable fonts (a render-blocking CSS import of both families today), unused JS on Home (anything the Home does not need is dynamic), image dimensions (CLS), the `data` chunk (185 KB raw) loaded for routes that do not need card data, long main-thread tasks at boot.
- **60 fps (WP3).** `app/e2e/perf-frames.spec.ts` (runs only with `PERF=1`) sets CDP `Emulation.setCPUThrottlingRate` 4, records `requestAnimationFrame` deltas and long tasks in the page during: the 13-move AI turn of `scenario=late` at speed 1×, a played card with DON!! attach, an attack arrow with a counter, and the review timeline scroll (the M1-26 case), and saves a Chrome trace (`browser.startTracing`, timeline and frame categories) per scenario. Pass line (the requirement): at 4×, p95 frame ≤ 20 ms, p99 ≤ 34 ms, at most 2% of frames over 25 ms, no long task over 100 ms inside an animation; at 1×, p99 ≤ 20 ms. The nightly asserts 1.5× of those and reports both. Ubuntu CI draws with software compositing, so CI numbers are pessimistic against a GPU; the owner may run `npm run perf:frames -- --headed` on the Mac for the reference. The board's animations are `transform` and `opacity` only (board.md §5.3); the likely defects are React re-renders per animation step, layout thrash from reading sizes, and the arrow's SVG path. Fixes are `contain`, `will-change` on the moving layer only, memoised cards and removing reads, never a lower frame target.
- **AI wait (WP3, M5a-20, DECISIONS 2026-11-27).** The Warlord's ms-mode wait was 1.8 to 4.1 s against a budget of 1,500 ms and a board.md target of 1.8 s. First split the wait with `performance.measure` marks (the message out, the worker's search start and end, the message back) into search, setup and transfer. Then warm the worker: spawn it and build the `AiSession` when Setup mounts (not at "Start"), run one 1-iteration plan to warm the JIT, and keep `peekNext` out of board time (M5a-20). The per-push test is deterministic (the warm-up message is sent at Setup; `peekNext` adds no board ms on the fake clock). The nightly reports `ai-turns` and keeps its 2,700 ms bound; if the wait is still over 1,800 ms the report says so and BACKLOG gets the item.

## Accessibility

**Lighthouse accessibility ≥ 90** is the floor, not the audit: it runs a subset of axe. It is in the same Lighthouse run (above).

**WCAG 2.2 AA audit, method.** Three layers, each with a stated limit:

1. **Automated, every route at both sizes (WP4).** `app/e2e/m10-audit.spec.ts` walks the route manifest (`app/e2e/support/audit-routes.ts`; a test fails if `App.tsx` or `routes/m9.ts` holds a path the manifest lacks) at 1280×720 and 1920×1080: axe with `wcag2a`, `wcag2aa`, `wcag21aa`, `wcag22aa` (zero violations; `incomplete` saved and read); the focus heading on route change; the tab sequence with focus not obscured (2.4.11, sampled up to 60 stops per route); target size (2.5.8) by box measurement; and the five environment checks of accessibility §11.7: **200% zoom and 400% reflow** (the viewport at half and a quarter of the CSS size: no horizontal scroll outside the board, which the 1.4.10 two-dimensional exception covers), **text spacing** (1.4.12 CSS injected; no clipped or overlapping text found by a scroll-size sweep), **forced colours**, **reduced motion** (no running transform transition), and **colour-vision emulation** (CDP `Emulation.setEmulatedVisionDeficiency` for four kinds, screenshots saved and every §6.1 row read). Output: `docs/design/a11y-passes/m10-automated.md`, generated.
2. **Manual checklist per success criterion the automation cannot judge (WP5).** `docs/design/a11y-passes/m10-wcag-audit.md` has one row per WCAG 2.2 A and AA criterion: how it is met, the evidence (a test, a spec line, a screenshot) or the manual step, who judged it, and the result. The manual rows (the automation cannot decide them) are 1.1.1 (art is decorative and every informative image has a name), 1.3.1 and 1.3.2 (DOM order against reading order on the board, review and builder), 1.3.3, 1.4.3 and 1.4.11 over card art (worst-case art, the SAMPLE watermark), 1.4.13 (hover content dismissible), 2.1.1 and 2.1.2 (no trap, including the board application region), 2.1.4 (single-key shortcuts can be turned off), 2.2.1 and 2.2.2 (drill timers, AI playback pause), 2.3.1 (no flash over three a second), 2.4.1 to 2.4.6 (skip link, titles, order, link purpose, more than one way, headings and labels), 2.5.1 to 2.5.3, 2.5.7 (no drag-only action), 3.1.1, 3.2.1 to 3.2.4 and 3.2.6, 3.3.1 to 3.3.4 and 3.3.7 (deck import errors, delete confirmations, nothing asked twice), 3.3.8 (no authentication: not applicable, said so), 4.1.2 and 4.1.3 (names, states and the live-region policy, which only a screen reader judges). Criteria that do not apply (1.2.x, 2.5.4, 3.3.8) are listed as such with the reason.
3. **Screen readers.** The agent cannot listen. NVDA: the scripted Guidepup passes on Windows (Chrome and Firefox), `script=all` plus the new `m10`. VoiceOver with Safari: the owner, by hand, from one printed sheet. Records are written to `docs/design/a11y-passes/` with versions. The claim in STATUS.md is exactly "automated axe on every route, scripted NVDA in Chrome and Firefox, the owner's VoiceOver pass", and it says no screen-reader user outside the project has used it (accessibility R10) unless S3's invitee does.

**Scripts the owner runs.** The M10 listening sheet (`docs/design/a11y-passes/M10-listening-pass.md`, generated by `scripts/a11y-sheet.ts` from the harness step arrays so it cannot drift) lists, in order, with VoiceOver keys and the expected phrases: M3 (the board), L (the learning slice), M7 (tutorial, coach), M8 (the review), M9 (matchup grid, drill, rules, progress) and the new **M10** (A1 About: heading, version line and links; E1 an unknown address: "Page not found" takes focus and its link goes home; U1 the update prompt is a polite status that does not steal focus; S1 the skip link and the shortcut sheet; O1 offline: the app loads, art falls back to text faces and says nothing assertive). Plus the one by-hand item no script covers: a whole game against the Warlord with the keyboard only (accessibility §11.7; S3 task 3.7). Estimated 90 minutes for the owner on his Mac, in two sittings.

## Release

**What ships.** Version **1.0.0** at `https://chrisdevine00.github.io/optcg-sim/`, deployed by the existing `deploy.yml` after green CI on `main`. `version.json` gains `release`; a post-deploy step fetches the live `version.json`, the home page and a deep link (`/cards`, which Pages answers from `404.html`) and fails the run if the build id differs from the one just built. The deployed URL goes into STATUS.md with the build id and the Lighthouse run against the live home page (the release evidence).
**Added surfaces (WP6).**
- **About** (`/about`, in the footer and Settings): what the app is; the unofficial, non-commercial notice (the same words as the footer and README); the version line from `version.json` (release, build, cards through, card count, meta as-of, engine version); **credits** (card data from optcgapi.com, hotlinked art with the SAMPLE watermark on every available image, tournament lists and play rates from Limitless, tier data from opmetagame, strategy sources from Shonen TCG and Bounty TCG as cited in the guides, the Comprehensive Rules as our paraphrase; fonts Inter and Fraunces under the SIL Open Font Licence 1.1); **third-party licences** (`third-party.txt`, generated at build by `scripts/licences.ts` from the production dependency tree; the build fails on a dependency with no licence or a strong-copyleft one); a "**Your data**" section (the privacy statement); how to report a problem.
- **Privacy statement (plain words).** No account, no server of ours, no analytics, no cookies we set. Games, decks, reviews and progress live in this browser's IndexedDB and localStorage and leave it only through Export. The only network requests after the app loads are card images from the art hosts listed, whose operators see your address as any website would; the service worker keeps the app and seen images for offline use. "Delete all my data" already exists in Settings → Data; the page links to it. An e2e records every request origin across Home, a game, the builder, the drills and About and fails on an origin outside the app's and the art hosts' (accessibility §11.1 "No network from logs and settings", extended).
- **Errors.** An `ErrorBoundary` at the root and one per route: "Something went wrong on this page. Your saved games and decks are not affected." with Reload, Go home and "Copy details" (version line, route, message; no game data). A worker crash is already handled (`crashed()`); a failed chunk load after an update says "Reload to get the new version" instead of a blank page. A render error never takes the saved data with it (tested by throwing in a route and reading the store afterwards).
- **Offline.** Already working (shell precache). New: a quiet `role="status"` line on Home and Settings when `navigator.onLine` is false ("You are offline. Everything works; card art you have not seen yet shows as text."), and the offline e2e extended to Home → Play → finish a hotseat turn offline.
- **404.** `Page not found` keeps focus on its heading and offers Home and the nav; tested for a deep unknown path. Pages answers unknown deep paths with status 404 and the app's page; users see the app, a crawler would see a 404. Accepted (no SEO goal); recorded.
- **Head and icons.** `favicon.svg` (our own mark, no Bandai imagery), a 180 px `apple-touch-icon.png`, `manifest.webmanifest` (name, short name, `display: standalone`, start URL under the base, colours from the tokens, 192 and 512 icons), `<meta name="description">`, `theme-color` for both schemes, `og:title` and `og:description` with no image. A test fails if the manifest's icons or start URL do not resolve in the build.
- **Docs.** `CHANGELOG.md` (Keep a Changelog; 1.0.0 summarises M0 to M10, names the known limits), README (deployed URL, legal, privacy, bug reports), `docs/legal/CREDITS.md` (the About page's credits in full with each source's terms note), `LICENSE` once the owner chooses (below).
- **CSP (cut-order item 1).** A `<meta http-equiv="Content-Security-Policy">` in the production build only: `default-src 'self'`; `img-src` the art hosts, `data:`, `blob:`; `worker-src 'self' blob:`; `connect-src 'self'` (plus the update and card endpoints if the e2e shows any). GitHub Pages cannot set headers, so this is the only way; the whole e2e suite runs against it.
**Versioning.** SemVer from 1.0.0. The app's `package.json` version is the release; `version.json.release` reads it. Data refreshes (cards, meta) are patch releases by their weekly PRs, which the CHANGELOG's "Unreleased" collects; the engine's `ENGINE_VERSION` stays separate (it versions records). A git tag `v1.0.0` and a GitHub release are the owner's go-ahead after S3.

## Visual regression and the test rules

PROMPT asks for visual-regression screenshots of the board, inspector, coach panel, review timeline and meta explorer at both sizes. M8 and M9 saved screenshots for a person to read and compared nothing. WP8 compares pixels: Playwright `toHaveScreenshot`, 20 baselines in `app/e2e/__visual__/` per project (board in Explore and Defend, inspector, coach, review timeline and study, meta tiles and grid, a drill item, rules, progress, builder, About, Settings), art blocked by routing the image hosts to an abort so every card is the text face (no Bandai art is committed or compared), animations disabled, clock and seeds fixed, `maxDiffPixelRatio` 0.002. Baselines are made on Linux only (a `workflow_dispatch` input updates them and uploads a PR-ready artifact; a Mac run skips them), because font anti-aliasing differs by OS. They run in the nightly and on dispatch, with the diff images uploaded on failure; per push keeps the saved screenshots and axe (renderer noise on a pixel diff is the non-defect failure `docs/runbooks/testing.md` keeps out of per-push suites; DECISIONS "M10 plan", lead amendment).
Every M10 test follows `docs/runbooks/testing.md`: no wall-clock assert per push (frames and Lighthouse are nightly and report numbers; the per-push tests check mechanisms: the warm-up message, the gate, the boundary), clocks injected or faked, waits as hang guards, rates by confidence interval (none expected), and each test names the revert that makes it fail.
